# Frontend UI Engineering

## Overview

Build production-quality user interfaces that are accessible, performant and visually polished. The goal is UI that looks like it was built by a design-aware engineer at a top company — not like it was generated by an AI. This means real design system adherence, proper accessibility, thoughtful interaction patterns and no generic "AI aesthetic."

## When to Use

- Building new UI components or pages
- Modifying existing user-facing interfaces
- Implementing responsive layouts
- Adding interactivity or state management
- Fixing visual or UX issues

## Verify With What the Project Has

Run the project's own test, type-check or lint commands. Don't install a framework, test runner or type checker just to check your work; if the project has none, review the code against the [Verification](#verification) list and say what you could not run.

Follow the [project approval rules](../../../AGENTS.md#authority) and the [verification requirements](../../../docs/reference/verification.md#definition-of-done). Use browser evidence for native interactions and layout.

## Component Architecture

### File Structure

Use the project's [TypeScript and React](../../../docs/reference/typescript-react.md) and [styling](../../../docs/reference/styling.md) conventions: `ReadonlyDeep` for immutable inputs, SCSS and React BEM for component styles and traditional BEM for shared styles.

Colocate everything related to a component:

```
src/components/
  TaskList/
    TaskList.tsx          # Component implementation
    TaskList.test.tsx     # Tests
    TaskList.stories.tsx  # Storybook stories (if using)
    use-task-list.ts      # Custom hook (if complex state)
    types.ts              # Component-specific types (if needed)
```

### Component Patterns

**Prefer composition over configuration:**

```tsx
// Good: Composable
<Card>
  <CardHeader>
    <CardTitle>Tasks</CardTitle>
  </CardHeader>
  <CardBody>
    <TaskList tasks={tasks} />
  </CardBody>
</Card>

// Avoid: Over-configured
<Card
  title="Tasks"
  headerVariant="large"
  bodyPadding="md"
  content={<TaskList tasks={tasks} />}
/>
```

**Keep components focused:**

```tsx
import { useId } from 'react';

import Button from '@/components/Button';

import type { ReadonlyDeep } from 'type-fest';

// TaskItemProps and TrashIcon come from the example's task feature.
// Good: Does one thing
export function TaskItem({
  onDelete,
  onToggle,
  task,
}: ReadonlyDeep<TaskItemProps>) {
  const checkboxId = useId();

  return (
    <li className="TaskItem">
      <input
        checked={task.done}
        id={checkboxId}
        type="checkbox"
        onChange={() => onToggle(task.id)}
      />
      <label className="TaskItem-Label" htmlFor={checkboxId}>
        <span
          className={
            task.done ? 'TaskItem-Title TaskItem-Title_done' : 'TaskItem-Title'
          }
        >
          {task.title}
        </span>
      </label>
      <Button
        aria-label={`Delete task: ${task.title}`}
        onClick={() => onDelete(task.id)}
      >
        <TrashIcon aria-hidden="true" />
      </Button>
    </li>
  );
}
```

**Separate data fetching from presentation:**

```tsx
// Container: handles data
export function TaskListContainer() {
  const { tasks, isInitialLoading, error, refetch, toggleTask, deleteTask } =
    useTasks();

  if (isInitialLoading) return <TaskListSkeleton />;
  if (error)
    return <ErrorState message="Failed to load tasks" retry={refetch} />;
  if (tasks.length === 0) return <EmptyState message="No tasks yet" />;

  return <TaskList tasks={tasks} onToggle={toggleTask} onDelete={deleteTask} />;
}

// Presentation: handles rendering
export function TaskList({
  tasks,
  onToggle,
  onDelete,
}: ReadonlyDeep<
  { tasks: Task[] } & Pick<TaskItemProps, 'onToggle' | 'onDelete'>
>) {
  return (
    <div className="TaskList">
      <ul role="list" className="TaskList-Items">
        {tasks.map((task) => (
          <TaskItem
            key={task.id}
            task={task}
            onToggle={onToggle}
            onDelete={onDelete}
          />
        ))}
      </ul>
    </div>
  );
}
```

## State Management

**Choose the simplest approach that works:**

```
Local state (useState)           → Component-specific UI state
Lifted state                     → Shared between components with a common owner
Context                          → Theme, auth, locale (read-heavy, write-rare)
URL state (searchParams)         → Filters, pagination, shareable UI state
Server state                     → Remote data with caching
Global store                     → Complex client state shared app-wide
```

Repeatedly passing props through components that do not use them can signal an awkward ownership boundary. Consider composition, context or restructuring when it solves that problem. Changes to architecture or dependencies require approval.

## Design System Adherence

### Reference-led UI quality

When the product needs a distinct visual direction, collect evidence before choosing a layout:

1. Search a trusted reference catalogue or use references supplied by the product team.
2. Study two or three relevant screens. Record decisions about hierarchy, density, navigation, controls, responsive behaviour and interaction states.
3. Turn those decisions into a short design contract before implementation. Name the screen's job, primary action, required states, responsive rules and patterns to reject.
4. Rebuild the useful structure in the product's own components, tokens, content and visual language. Never copy another product's branding, proprietary text, imagery or exact layout.

Use references as evidence, not as templates or approval. Document assumptions if references are unavailable and check against the existing design system. Get user approval for design and UX decisions not covered by the approved plan.

### Avoid the AI Aesthetic

AI-generated UI has recognisable patterns. Avoid all of them:

| AI Default                         | Why It Is a Problem                                                                           | Production Quality                                      |
| ---------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| Purple/indigo everything           | Models default to visually "safe" palettes, making every app look identical                   | Use the project's actual colour palette                 |
| Excessive gradients                | Gradients add visual noise and clash with most design systems                                 | Flat or subtle gradients matching the design system     |
| Rounded everything (`rounded-2xl`) | Maximum rounding signals "friendly" but ignores the hierarchy of corner radii in real designs | Consistent `border-radius` from the design system       |
| Generic hero sections              | Template-driven layout with no connection to the actual content or user need                  | Content-first layouts                                   |
| Lorem ipsum-style copy             | Placeholder text hides layout problems that real content reveals (length, wrapping, overflow) | Realistic placeholder content                           |
| Oversized padding everywhere       | Equal generous padding destroys visual hierarchy and wastes screen space                      | Consistent spacing scale                                |
| Stock card grids                   | Uniform grids are a layout shortcut that ignores information priority and scanning patterns   | Purpose-driven layouts                                  |
| Shadow-heavy design                | Layered shadows add depth that competes with content and slows rendering on low-end devices   | Subtle or no shadows unless the design system specifies |

### Spacing and Layout

Use a consistent spacing scale. Don't invent values:

```css
/* Use the scale: 0.25rem increments (or whatever the project uses) */
/* Good */
padding: 1rem; /* 16px */
/* Good */
gap: 0.75rem; /* 12px */
/* Bad */
padding: 13px; /* Not on any scale */
/* Bad */
margin-top: 2.3rem; /* Not on any scale */
```

### Typography

Respect the type hierarchy:

```
h1 → Page title (one per page)
h2 → Section title
h3 → Subsection title
body → Default text
small → Secondary/helper text
```

Don't skip heading levels. Don't use heading styles for non-heading content.

### Colour

- Use semantic colour tokens: `text-primary`, `bg-surface`, `border-default` — not raw hex values
- Ensure sufficient contrast (4.5:1 for normal text, 3:1 for large text)
- Don't rely solely on colour to convey information (use icons, text or patterns too)

## Accessibility (WCAG 2.2 AA)

WCAG 2.2 AA is the [web target](../../../docs/reference/accessibility.md) for editor and preview interaction, not proof of conformance or exported-PDF accessibility.

Use the [WAI-ARIA APG patterns](https://www.w3.org/WAI/ARIA/apg/patterns/) for keyboard and semantics guidance on menus, dialogs, tabs, listboxes and comboboxes. A composite can have one Tab stop and use arrow keys within it; verify the actual interaction.

### Keyboard Navigation

```tsx
// Every interactive element must be keyboard accessible
<button onClick={handleClick}>Click me</button>        // ✓ Focusable by default
<div onClick={handleClick}>Click me</div>               // ✗ Not focusable
<div role="button" tabIndex={0} onClick={handleClick}    // ✓ But prefer <button>
     onKeyDown={(e) => {
       if (e.key === 'Enter') handleClick();
       if (e.key === ' ') e.preventDefault();
     }}
     onKeyUp={(e) => {
       if (e.key === ' ') handleClick();
     }}>
  Click me
</div>
```

### ARIA Labels

Give controls meaningful accessible names. Also make a field's purpose and any needed instructions available to all users, using visible labels or clear visible context. An accessible name alone does not provide visible guidance.

```tsx
// Label interactive elements that lack visible text
<button aria-label="Close dialog"><XIcon aria-hidden="true" /></button>

// Label form inputs
<label htmlFor="email">Email</label>
<input id="email" type="email" />

<label htmlFor="task-search">Search tasks</label>
<input id="task-search" type="search" />
```

### Focus Management

Use `showModal()` or the project’s native modal pattern. `<dialog open>` alone is non-modal. Verify initial focus and focus containment while the modal is open. Check that Escape and the close control both dismiss it and that focus returns to the opener (or a logical fallback if it no longer exists).

```tsx
function TaskDetailsDialog() {
  const dialogRef = useRef<HTMLDialogElement>(null);
  const titleId = useId();

  return (
    <>
      <button
        type="button"
        onClick={(e) => {
          e.currentTarget.focus();
          dialogRef.current?.showModal();
        }}
      >
        Task details
      </button>
      <dialog ref={dialogRef} aria-labelledby={titleId}>
        <h2 id={titleId}>Task details</h2>
        <p>Review the task before marking it complete.</p>
        <form method="dialog">
          <button type="submit">Close</button>
        </form>
      </dialog>
    </>
  );
}
```

### Meaningful Empty and Error States

If an action produces an empty result without moving focus, announce the result through an existing status region, not by making the whole empty state live.

```tsx
// Don't show blank screens
function TaskList({
  tasks,
  onCreateTask,
}: ReadonlyDeep<{ tasks: Task[]; onCreateTask: () => void }>) {
  if (tasks.length === 0) {
    return (
      <div className="TaskList-Empty">
        <TasksEmptyIcon className="TaskList-EmptyIcon" aria-hidden="true" />
        <h3 className="TaskList-EmptyTitle">No tasks</h3>
        <p className="TaskList-EmptyHint">
          Get started by creating a new task.
        </p>
        <Button className="TaskList-EmptyAction" onClick={onCreateTask}>
          Create Task
        </Button>
      </div>
    );
  }

  return <ul role="list">...</ul>;
}
```

## Responsive Design

Design for narrow space first, then expand. Components adapt to an ancestor container, not to the viewport or to themselves. For the data/presentation `TaskList` example:

```scss
.TaskList {
  container: task-list / inline-size;
}

.TaskList-Items {
  display: grid;
  grid-template-columns: minmax(0, 1fr);
  gap: 1rem;
}

@container task-list (min-width: 30rem) {
  .TaskList-Items {
    grid-template-columns: repeat(2, minmax(0, 1fr));
  }
}

@container task-list (min-width: 48rem) {
  .TaskList-Items {
    grid-template-columns: repeat(3, minmax(0, 1fr));
  }
}
```

Use viewport-size queries for the `AppLayout` shell. Pointer, hover and user-preference queries (such as reduced motion) are separate and can still be used in components. Probe narrow and wide containers at the same viewport, including a narrow editor panel on desktop. Viewport widths such as 320px, 768px, 1024px and 1440px are useful probes, not sufficient coverage or fixed release criteria.

## Loading and Transitions

`TaskListContainer` uses the skeleton only on initial load. For retry or refetch, keep a `role="status"` element mounted before the action and update its visible text for meaningful waiting and outcome messages without moving focus just to announce them. Use urgency appropriate to the interaction, not a live region on every state.

```tsx
// Initial loading: visible text with decorative skeletons
function TaskListSkeleton() {
  return (
    <div className="TaskListSkeleton">
      <p>Loading tasks…</p>
      <div className="TaskListSkeleton-Items" aria-hidden="true">
        {Array.from({ length: 3 }).map((_, i) => (
          <div key={i} className="TaskListSkeleton-Item" />
        ))}
      </div>
    </div>
  );
}
```

```scss
.TaskListSkeleton-Items {
  display: grid;
  gap: 0.5rem;
}

.TaskListSkeleton-Item {
  height: 1rem;
  background-color: currentColor;
  opacity: 0.2;
}
```

```tsx
// Optimistic updates for perceived speed, when the approved data layer supports them
function useToggleTask() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: toggleTask,
    onMutate: async (taskId) => {
      await queryClient.cancelQueries({ queryKey: ['tasks'] });
      const previous = queryClient.getQueryData<ReadonlyDeep<Task[]>>([
        'tasks',
      ]);

      queryClient.setQueryData<ReadonlyDeep<Task[]>>(['tasks'], (old) =>
        old?.map((t) => (t.id === taskId ? { ...t, done: !t.done } : t)),
      );

      return { previous };
    },
    onError: (_err, _taskId, context) => {
      queryClient.setQueryData(['tasks'], context?.previous);
    },
  });
}
```

## Common Rationalisations

| Rationalisation                                | Reality                                                                                      |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| "Accessibility is a nice-to-have"              | It's a legal requirement in many jurisdictions and an engineering quality standard.          |
| "We'll make it responsive later"               | Retrofitting responsive design is 3x harder than building it from the start.                 |
| "The design isn't final, so I'll skip styling" | Use the design system defaults. Unstyled UI creates a broken first impression for reviewers. |
| "This is just a prototype"                     | Prototypes become production code. Build the foundation right.                               |
| "The AI aesthetic is fine for now"             | It signals low quality. Use the project's actual design system from the start.               |

## Red Flags

- Components over 200 lines warrant a closer look for mixed responsibilities. Split only if the separation makes the component clearer.
- Components mixing responsibilities that would be clearer apart
- Inline styles or arbitrary pixel values
- Missing error states, loading states or empty states
- No keyboard navigation testing
- Colour as the sole indicator of state (red/green without text or icons)
- Generic "AI look" (purple gradients, oversized cards, stock layouts)

## Verification

After building UI, check what you can with the project's own tooling, and review the rest against this list. Don't add dependencies or install toolchains only to verify; say which checks you couldn't run.

- [ ] Component renders without new console errors; report unrelated baseline errors separately.
- [ ] All interactive elements are keyboard accessible. Tab between controls; test arrow keys inside composites and dismissal and focus return for modals where applicable.
- [ ] Screen reader can convey the page's content and structure. A tree inspection alone does not verify what is announced.
- [ ] Responsive: probe viewport widths such as 320px, 768px, 1024px and 1440px. For a component, also test narrow and wide containers at the same viewport.
- [ ] Loading, empty, error, success and permission states handled when applicable
- [ ] Follows the project's design system (spacing, colours and typography)
- [ ] The rendered result passes a final UI-specific finish-gate review
- [ ] No unresolved accessibility warnings attributable to the change in DevTools or axe-core. Report unrelated findings separately; a clean web audit does not verify an exported PDF.
